## 0. 写在前面

我的开发习惯是"先让它跑起来，再让它跑对，最后让它跑稳"。这个项目基本就是按这三步走的：第一步把 Flask、MySQL、Vue、小程序四套环境凑齐，能通一个 `/api/ping` 就高兴半天；第二步补业务，把"看资源—看地图—上报足迹—大屏跳动"这条链子接通；第三步才发现真正难的不是写功能，而是那些**不报错、只是不工作**的地方——健康检查在说谎、缓存失效没触发、广播发出去了但没人收到。

所以这份日志里，功能部分的篇幅不大（因为功能本身没什么好写的，照着接口契约写就行），大头全在踩坑上。有些坑很蠢，比如抄了个 Linux 的 Redis 启动参数在 Windows 上跑不起来；有些坑则让我第一次认真去读库的源码和协议文档，比如 `HELLO 3`。都记下来了，算是给自己留个错题本。

**阶段小记。**

阶段 1 其实没什么技术含量，全是环境。Python 里缺 eventlet，装；MySQL 里没有库，写脚本建；建表时纠结了一下"日志表要不要分两张"，最后决定用一张 `system_log` 加 `source` 字段区分后台操作和游客行为——现在看这个决定是对的，因为大屏统计时不用 UNION 两张表。

阶段 2 是分水岭。写 `/api/log` 的时候我反复问自己一个问题：浏览量到底该在"看详情"的时候加，还是在"上报足迹"的时候加？如果详情接口自己去加，那我在后台预览一次也会 +1，数据就脏了。最后定的是**详情接口干干净净，所有计数只认 `/api/log`**。这个决定后面救了我——演示时反复刷新页面，PV 一次都没虚高。

阶段 3 的坑在设计上：一开始大屏是嵌在后台布局里的，侧边栏一占，图表就挤成一团。后来把它改成独立的全屏路由，才算像个"大屏"。另外 Leaflet 那部分我纠结了很久要不要用在线瓦片，最后决定用本地 GeoJSON 画海宁边界——理由很实际：答辩教室的网不一定靠谱，断网了至少地图轮廓还在。

阶段 4 是把双刃剑。Uni-app 一套代码编译两端很爽，但小程序的各种限制也很磨人，比如不能直接打开外部链接，只能"复制 + 提示"。我一开始觉得这是妥协，后来想通了：反正定位就是零支付纯导流，复制链接反而是最不容易出事的方式。

阶段 5 是最痛苦也收获最大的一段，整节 3.1—3.5 的坑全在这儿。Redis 接进去之后我才意识到，"缓存"不只是加个 `GET`，还要考虑写操作怎么失效、服务挂了怎么办、恢复了怎么自己爬起来。这三件事没想清楚，缓存就是负债。

阶段 6—7 是纯体力活，但有个意外收获：为了写测试报告去压测，才发现缓存带来的差距有 3.3 倍——这个数字后来成了论文里最硬的一段论证。所以文档不是"事后补的作业"，写文档的过程本身就在帮你验证系统。

## 3. 核心技术难点攻关记录

这一节是重点。前面 7 条是我**真撞上去**的，第 8 条的两个坑是我**看文档提前躲过去**的（我会标清楚，免得答辩被追问细节时露馅），第 9 条是非代码的坑。

### 3.1 Redis 连不上：`HELLO 3` 是什么鬼

**现象。** Redis 启动好了，`redis-cli ping` 返回 `PONG`，但后端 `/api/ping` 里 `redis` 一直是 `false`，日志里躺着这么一行：

```
WARNING in cache: Redis 不可用，缓存降级：unknown command 'HELLO', with args beginning with: '3',
```

**排查。** 第一反应是端口不对或密码问题，但 `redis-cli -h 127.0.0.1 -p 6379 ping` 明明是通的。于是我单独写了个十行小脚本，把 `redis.Redis(host=..., port=6379).ping()` 拿出来跑，一下就复现了。接着试了 `protocol` 参数：

```python
>>> redis.Redis(port=6379, protocol=2).ping()
True
>>> redis.Redis(port=6379, protocol=3).ping()
ResponseError: unknown command `HELLO`, with args beginning with: `3`
```

**根因。** 我装的是 redis-py 8.1，默认走 RESP3 协议，连上就发 `HELLO 3` 做握手；但 Windows 上能拿到的 Redis 最高只到 5.0.14（tporadowski 维护的那个移植版），`HELLO` 命令是 Redis 6 才有的。所以不是网络问题，是**客户端协议版本比服务端新**。

**解决。** 把 `redis-py` 降到 5.0.8，并在连接时显式写死 `protocol=2`，`requirements.txt` 里也锁了版本。

**回头看。** 以前只听说过"客户端和服务端版本要匹配"，这次是真被教做人。而且这个坑很阴：它不报连接超时，报的是一个你根本没调过的命令，很容易往网络或密码方向查半天。另外这也算一个客观约束——本机就是只能用 Redis 5，所以"生产环境建议 6/7"这句话我写进了论文的局限里，不装。

### 3.2 `--save ""` 直接把 Redis 干趴了

**现象。** 我想演示环境不需要持久化，按 Linux 教程写了：

```
redis-server --port 6379 --bind 127.0.0.1 --save "" --appendonly no
```

结果 Redis 根本没起来，退出码 1，报：

```
Invalid argument during startup: Not enough parameters available for --save
```

**排查。** 去掉 `--save ""` 就能起，说明问题就出在这个参数上，不是端口或权限。

**根因。** Linux 版用空字符串表示"关闭 RDB 快照"，而 Windows 移植版的参数解析器不吃这种写法，它要求 `--save` 后面必须跟两个数字（秒数 + 变更次数）。

**解决。** 改成 `--save 3600 1`（一小时一次、至少 1 个键变更才落盘），代价可以忽略。

**回头看。** 抄命令真的要看平台。这条算不上技术难题，但它卡了我几分钟，而且如果没注意退出码，会以为"Redis 装坏了"。

### 3.3 前端构建被 esbuild 拦住：`Access is denied`

**现象。** `npm run build` 跑到渲染阶段突然挂掉：

```
[vite:esbuild-transpile] remove C:\Users\HP\AppData\Local\Temp\esbuild-3cf138ae...: Access is denied.
x Build failed in 15.63s
```

**排查。** 一开始怀疑是杀毒软件锁了临时文件，重试一次还是同样的报错，而且路径是系统 TEMP 目录。于是换成"让它别用系统 TEMP"的思路，把 `TEMP`/`TMP` 指到项目里的 `.tmp`：

```powershell
$env:TEMP = '.\web-frontend\.tmp'; $env:TMP = $env:TEMP
npm run build
```

**根因。** esbuild 在收尾时会删除自己写在系统 TEMP 下的临时文件，这个删除动作被拦住了，于是整次构建被判失败——报错在"删文件"，其实跟我的代码一点关系都没有。

**结果。** 直接过了，`✓ built in 16.93s`，dist 20 个文件、2.9 MB。

**解决。** 构建前设 TEMP 到项目内目录，并把这条写进了 `README.md` 和测试报告的缺陷记录里（BUG-01）。

**回头看。** 报错里出现 `remove ... Access is denied` 时，八成不是代码问题，而是工具在清理临时文件时权限被拦。换个可写的临时目录比查代码快得多。

### 3.4 健康检查"说谎"：Redis 都停了它还报正常

**现象。** 我手动把 Redis 进程杀掉，然后请求 `/api/ping`，返回的 `redis` 字段还是 `true`。

**排查。** 看代码发现第一版是这么写的：

```python
def redis_alive():
    client = get_redis()
    return client is not None      # 只判断"对象在不在"
```

**根因。** 连接对象是模块级单例，一旦创建过就一直非空，所以进程死了它"看起来"还存在。

**解决。** 改成真发一次 `PING`，异常就返回 False 并把单例丢掉。

**回头看。** 健康检查必须"真探活"，不能看缓存状态。这个道理写在书上很轻，自己写的时候就容易图省事。

### 3.5 Redis 关掉再打开，后端一直连不上

**现象。** 修完 3.4 之后，停 Redis 能正确报 `false` 了；但把 Redis 重新启动，等了半分钟 `redis` 还是 `false`，像抽风一样。

**排查。** 日志里一点重连的动静都没有，说明代码压根没再去连。翻回 `get_redis()` 才看清问题。

**根因。** "失败也被缓存了"——第一版用一个 `_client_checked` 布尔量标记"试过了"，失败后置 True，于是后续请求直接返回 None，永远不会再试。

**解决。** 换成带时间窗的惰性重连——失败后记下时间戳，5 秒内不重试（避免每个请求都卡在 1 秒连接超时上），超过 5 秒允许再试一次：

```python
now = time.time()
if _last_attempt and (now - _last_attempt) < RETRY_INTERVAL:
    return None
_last_attempt = now
```

**结果。** 实测：停 Redis → `redis=false`；重启 → 7 秒后自动变回 `true`，缓存也恢复写入，全程没重启后端。

**回头看。** "降级"和"自愈"是两件事。只做降级，服务能活着但永远回不到好状态；加上重试间隔，才算闭环。

### 3.6 后台管不了已下架的资源

**现象。** 做资源管理页时发现：把一条资源下架，它从表格里消失了，而且再也点不回来——因为列表接口只返回 `status=1`。

**排查。** 先查数据库，`status` 确实是 0；再回头看接口，发现列表的 SQL 里写死了 `Attraction.status == 1`。

**根因。** 公开接口只返回上架资源是对的（游客不该看到下架的），但我把**同一个接口**拿去给后台用了，语义就错了。

**解决。** 新增 `GET /api/attractions/admin`，要求 JWT，返回全部状态并支持按 `status` 过滤；公开接口保持不变。

**回头看。** "同一个接口给两端用"看着省事，其实是把权限和语义混在一起。这次只是功能问题，严重一点就是越权。

### 3.7 中文一进命令行就乱码

**现象。** 想用 `python -c` 跑个短脚本读写带中文的路径，直接报：

```
  File "<string>", line 3
    src = rD:\homework\����\����
            ^
SyntaxError: invalid syntax
```

**排查。** 换成纯英文路径就能跑，一加中文就挂，反复试了三次都一样，于是把方向从"脚本逻辑写错"转到"参数在传递时被改了编码"。

**根因。** 命令行参数的编码和 Python 源文件的编码不是一回事，中文在传参途中被按系统代码页解释了一遍，路径自然就废了。

**解决。** 从此不写长 `python -c`，一律"把脚本写成 `.py` 文件再执行"，并给输出加 `PYTHONIOENCODING=utf-8`。

顺带踩到第二个：用 PowerShell 跑 `.ps1` 辅助脚本时报

```
无法加载文件 D:\homework\毕设\_tmp_tools\convert_doc.ps1。未对文件进行数字签名。无法在当前系统上运行该脚本。
```

改成用 `powershell -NoProfile -ExecutionPolicy Bypass -File xxx.ps1` 调用就绕过了。

**回头看。** 这类问题不是"技术"，是环境配置，但它能耗掉你半小时。经验：**凡是带中文路径/中文内容的自动化脚本，一律落盘成文件，别塞进命令行**。

### 3.8 看文档提前躲过去的两个坑（未实际触发）

这两个我**没有真的报错过**，是在动手前翻文档发现的。写在这里是为了答辩时能讲清楚"为什么这么选"，同时也提醒自己别把话说过头。

**（1）`socketio.emit` 和 `flask_socketio.emit` 不是一回事。**
我这条链路是：小程序发 HTTP 请求 → 后端写库 → 广播给大屏。触发广播的地方是**一个普通 HTTP 请求**，它自己并不持有 WebSocket 连接。如果按网上示例写成 `from flask_socketio import emit; emit('new_data', data)`，那就变成"只回给当前请求上下文里的那个 socket"——而这个上下文根本不存在，结果就是**接口返回 200、大屏纹丝不动、还不报错**。所以从一开始就用了全局实例的 `socketio.emit(..., namespace="/ws")`，并单独写了 `tests/ws_probe.py` 用独立进程去验证，而不是靠"我看它应该是好的"。

**（2）JWT 的 `identity` 必须是字符串。**
flask-jwt-extended 4.x 起强制要求，写 `identity=str(admin.id)`，取出来再 `int()` 转换。这个如果没注意，会得到一个语焉不详的报错。

**回头看。** 这两个"没踩到的坑"其实比踩到的更值得记：因为它们不报错，只是安静地不工作，排查成本最高。

### 3.9 两个非代码的坑

**（1）两份文献 PDF 是坏的。** `文献\9.肖丽平` 和 `文献\11.夏斌斌` 各只有 1 页，内容是"抱歉，下载链接已失效，请您重新下载"。解析出来只有 44 个字符。这两篇只能靠题录信息引用，正文观点拿不到，写文献综述时确实缺了一块，只能换别的文献补。

**（2）mermaid 渲染翻车。** 论文插图我用 mermaid.ink 在线渲染成 PNG，6 张里第 5 张一直 `HTTP Error 400: Bad Request`，服务端说是 `Unknown diagram error`。试了半天发现是节点标签里混了英文双引号（`A[详情页点击"前往..."）`），换成「」就过了。而"系统分层架构图"不管怎么改都 400，最后我**放弃画图，改成一张三列的分层表格**——讲得清楚比画得好看重要，答辩时表格反而更好讲。

## 4. 压测与优化验证

### 4.1 怎么压的

不想装 Locust/JMeter，就用标准库写了个 `tests/bench.py`：线程池 + `urllib`，每场景固定 200 次请求、10 个线程并发，记录每次耗时后算 RPS 和 P50/P95/P99。压三个地方：走数据库的列表、走 Redis 缓存的地图点位、以及写库的埋点接口。

### 4.2 三组数据

| 场景 | 错误数 | RPS | 平均 | P50 | P95 | P99 |
|---|---|---|---|---|---|---|
| 资源列表（MySQL） | 0 | 154.3 | 60.5 ms | 55.0 | 77.9 | 223.7 |
| 地图点位（Redis 缓存） | 0 | **513.7** | **18.0 ms** | 17.3 | **32.3** | 35.8 |
| 足迹写入（写库+统计+广播） | 0 | 62.4 | 158.2 ms | 157.2 | 189.7 | 198.9 |

**缓存到底省了什么？** 同一份点位数据，走数据库要经过 SQLAlchemy 查询、对象实例化、逐条 `to_dict()`；走缓存只是一次 `GET` + `JSON.loads`。所以平均延迟从 60.5 ms 掉到 18.0 ms（降约 70%），RPS 从 154 涨到 514（约 3.3 倍）。这组对比后来直接写进了论文的"缓存价值"段落，比空口说"提高了性能"有说服力得多。

**为什么写接口这么慢？** 158 ms 里干了一件完整的事：插日志 → 原子自增浏览量 → 算今日 PV/UV/外链点击（两次聚合）→ 广播。看起来慢，但埋点是"发后不理"（客户端不 `await`），游客根本没感觉。真要优化，下一步是把统计从"每次请求都算"改成 Redis 计数器。

**P99 比 P95 高不少（223 ms vs 78 ms）**，说明有长尾，跟单进程 eventlet 的协作式调度排队有关。这也就是为什么我在论文里把"多实例 + Redis 消息队列"写成了后续工作——`message_queue` 这个口子已经留好了。

### 4.3 WebSocket 断线重连与心跳

这块单独说，因为它是"看起来能用"和"现场不断"的分界线。

**客户端（大屏）**

```javascript
socket = io('/ws', {
  path: '/socket.io',
  transports: ['websocket', 'polling'],   // 弱网自动退回长轮询
  reconnection: true,
  reconnectionDelay: 1000,                // 首次 1s
  reconnectionDelayMax: 8000              // 指数退避，最大 8s
})
```

socket.io 自带重连，但它只保证"连接回来"，不保证"数据没断"。所以我又加了一层兜底：**断线期间每 15 秒拉一次 `/api/stats/overview`**，这样即使 WS 一直连不上，大屏也不会定格成一张死图。

**服务端**

- `connect` / `disconnect` 里维护一个在线计数，并在 `/api/ping` 的 `ws_online` 字段暴露出来，调试时能确认"到底有没有人连着"；
- 提供 `ping → pong` 事件，前端可以拿它做探活（比依赖浏览器事件更可靠）；
- 广播走 `socketio.emit`，多实例时经 Redis Pub/Sub 传播；单实例或 Redis 挂了就退回进程内广播。

**降级验证**：停掉 Redis → 接口照常返回（缓存失效但回源数据库）→ 重启 Redis → 7 秒内自动恢复。这一串是实测的，不是设计的。

## 5. 项目现状总结

| 维度 | 现状 |
|---|---|
| HTTP 接口 | **15 个**：认证 3（登录/信息/改密）、资源 8（列表/后台列表/详情/地图/元数据/增删改/上下架）、足迹 2（上报/查询）、统计 1、健康检查 1 |

| Web 页面 | 4 个：登录、运营概览、资源管理、实时大屏 |
| 小程序页面 | 5 个：首页、地图、列表、详情、我的 |
| 数据 | 3 张表；12 个海宁点位跨 7 个镇街；458 条近 7 天演示足迹 |
| 产物 | Web dist 20 文件 / 2.9 MB；mp-weixin 30 文件 / 98 KB；h5 18 文件 / 282 KB |
| 链路 | 小程序上报 → 落库 → 统计 → WS 广播 → 大屏跳动，**端到端打通**；直连和经 Vite 代理两条路径都验过 |

## 附：错题本速查表（答辩前扫一眼）

| 报错关键词 | 一句话解法 |
