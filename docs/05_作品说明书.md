## 摘要

在数字乡村战略持续推进的背景下，浙江省作为全国数字乡村引领区，已在智慧农业与乡村数字治理方向形成大量成果，但面向公众的农文旅资源展示与空间导览环节仍存在明显短板：资源信息分散、缺乏空间关联、运营方难以感知真实客流。针对上述问题，本文设计并实现了一个面向嘉兴海宁市的乡村农文旅信息展示与服务平台。

平台采用"Web 管理端 + 微信小程序端"双端协同架构，两端共用同一套后端服务与数据库。后端基于 Flask 构建 RESTful 接口，使用 SQLAlchemy 完成对象关系映射，采用 JWT 实现无状态身份认证，并通过 Flask-SocketIO 与 Redis Pub/Sub 构建实时消息通道；Web 端基于 Vue3 + Vite + Element Plus 实现管理后台，使用 ECharts 完成数据可视化大屏，使用 Leaflet 与海宁市 GeoJSON 边界实现离线可用的资源空间分布展示；小程序端基于 Uni-app 开发，接入微信原生地图组件完成游客导览，并以匿名设备会话号记录浏览足迹。平台坚持"零支付纯导流"定位，不涉及任何在线交易，农产品与商品仅提供外链跳转。

系统实现后进行了功能、性能与异常场景测试：共设计并执行 34 个用例，全部通过；在 10 并发、每场景 200 次请求的压测下，资源列表接口 P95 为 77.9 ms，引入 Redis 缓存后的地图点位接口 P95 为 32.3 ms（较数据库直查平均延迟降低约 70%，吞吐提升约 3.3 倍），浏览足迹写入接口平均 158.2 ms，三场景错误率均为 0；在 Redis 停机场景下 HTTP 接口保持可用，重启后 7 秒内自动恢复连接。结果表明，该平台在轻量级技术栈下实现了多端数据一致与秒级实时同步，可为县域尺度的乡村农文旅信息化建设提供可复制的工程参考。

**关键词**：数字乡村；农文旅融合；WebGIS；多端协同；WebSocket；Flask

## Abstract

Against the backdrop of China's digital village strategy, Zhejiang Province, as the national leading pilot area, has produced substantial achievements in smart agriculture and rural digital governance. However, public-facing services for displaying rural agriculture-culture-tourism (ACT) resources and providing spatial guidance remain weak: information is scattered, spatial relationships are absent, and operators cannot perceive real visitor traffic. To address these issues, this thesis designs and implements a rural ACT information display and service platform for Haining City, Jiaxing.

The platform adopts a dual-terminal collaborative architecture consisting of a Web administration terminal and a WeChat Mini Program terminal, both sharing a single backend service and database. The backend is built on Flask with RESTful APIs, SQLAlchemy for object-relational mapping, and JWT for stateless authentication; a real-time channel is constructed with Flask-SocketIO and Redis Pub/Sub. The Web terminal is implemented with Vue3, Vite and Element Plus, featuring an ECharts-based visualization screen and a Leaflet map that renders the administrative boundary of Haining from local GeoJSON, which remains functional offline. The Mini Program is developed with Uni-app, integrating the native WeChat map component for tourist navigation and recording browsing footprints with an anonymous device session identifier. The platform follows a "zero-payment, pure redirection" principle: no online transaction is involved, and product information only provides external links.

Functional, performance and abnormal-scenario tests were carried out. A total of 34 test cases were designed and executed, all of which passed. Under 10 concurrent workers and 200 requests per scenario, the P95 latency of the resource list API was 77.9 ms, that of the map endpoint with Redis caching was 32.3 ms (about 70% lower average latency and roughly 3.3 times higher throughput than direct database queries), and the footprint-writing API averaged 158.2 ms, with zero errors in all three scenarios. When Redis was stopped, HTTP endpoints remained available and the connection was automatically restored within 7 seconds after restart. The results demonstrate that the platform achieves multi-terminal data consistency and second-level real-time synchronization on a lightweight stack, providing a replicable engineering reference for county-level rural ACT informatization.

**Keywords**: digital village; agriculture-culture-tourism integration; WebGIS; multi-terminal collaboration; WebSocket; Flask

## 第 1 章 绪论

### 1.1 研究背景

自《数字乡村发展战略纲要》与《数字乡村发展行动计划（2022—2025 年）》发布以来，数字乡村建设从试点探索走向全面铺开。浙江省自 2018 年起陆续出台《浙江省数字乡村建设实施方案》，2019 年启动未来乡村探索，2023 年成为全国唯一的数字乡村引领区，在农业生产数字化、乡村数字治理等方面走在全国前列。

然而，建设的广度并不等于服务的深度。张彬凯等对浙江省 2021 年 1 月至 2022 年 7 月间 125 个数字乡村领域政府信息化项目的统计分析显示：县（市、区）级与乡镇（街道）级项目合计 108 个，占比 86.4%；乡村数字治理与乡村数字经济两类场景合计 98 个，占比 78.4%；单体投资规模普遍偏小，74.4% 的项目金额低于 300 万元。这组数据揭示出两个事实：其一，数字乡村建设的主战场已经下沉到县域与乡镇；其二，主流形态是轻量化、场景化的小型应用。

与此同时，面向公众的"农文旅资源展示"环节相对薄弱。以嘉兴为例，本地最具代表性的农业信息化平台"种粮宝"聚焦于粮食补贴发放与田块管理，通过数据仓与管理端、服务端的三段式架构，将补贴处理从 9 个步骤压缩到 3 个、发放周期从 5 个月缩短到 10 个工作日，实现了省—市—县—乡—村五级数据联动。但其服务对象是监管部门与种粮主体，业务链局限于粮食生产，并未向公众提供农文旅内容的展示与空间导览。

现实中的乡村农文旅信息，仍大量依赖社交软件的零散传播：一条采摘信息可能出现在短视频评论区，一个古镇的活动可能只存在于公众号推文中。游客难以"按空间"检索目的地，运营方也难以判断哪些资源真正被关注。这正是本文试图切入的空白。

### 1.2 研究意义

**理论意义**。姚清晨等对 197 篇文献的系统综述提出了"技术嵌入—为人赋能"的张力框架，并归纳出数字缺失、数字悬浮、数字鸿沟、数字负担、数字形式主义五类困境。其中"数字悬浮"指新的技术架构因脱离乡村实际需求而被悬置，"数字负担"指多套系统造成的重复填报。本文从轻量级架构切入，探讨如何用低门槛的技术组合（微框架、跨平台编译、免安装小程序）降低使用负担，并以真实的运行日志而非虚构的宏观数据作为评价依据，为中小规模乡村信息系统的设计提供了可操作的参照。

**应用意义**。本文以海宁市为空间范围，构建了覆盖 12 个资源点位、7 个镇街的农文旅信息平台。对游客而言，小程序提供了"地图上一眼看懂哪里有果园、哪里有古镇"的入口；对运营方而言，Web 后台提供了内容维护能力，数据大屏则把浏览足迹实时转化为可视化指标。平台刻意不涉及在线交易，把交易留给成熟电商平台，自身专注于"被发现"这一环节，从而规避了乡村中小主体难以承接电商运营的现实困难。

### 1.3 国内外研究现状

#### 1.3.1 国内研究现状

国内的相关工作大体可分为三个方向。

**其一是宏观政策与数字乡村治理研究。** 姚清晨等指出，当前乡村数字治理存在理论深度不足、研究碎片化的问题，并强调应从"技术是否被嵌入"转向"人是否被赋能"。张彬凯等的项目统计则从供给侧印证了建设重心下沉与投入轻量化的趋势。沈项阳在探讨浙江数字乡村引领区的转型路径时进一步指出，即便在起步较早的浙江，仍存在基础设施覆盖不足、农村居民数字素养偏低、地方特色应用"与省级平台融通不够、实用性不强"、区域发展"北强南弱"等结构性困境。其中"实用性不强"一条，直指大量平台重建设、轻运营的通病。

**其二是农业与文旅信息系统的架构实践。** 邱慕涛基于 Flask 构建数据管理平台，采用"前端界面层—控制处理层—业务逻辑层—数据管理层"四层划分，实测表明该架构在中小并发下运行稳定：50 并发时响应时延约 410 ms、请求成功率 94.02%，但作者明确指出瓶颈来自 SQLite 写锁与事务提交的耦合，这为本文改用 MySQL 与 Redis 提供了反面依据。邓应卓等基于 HTML5 与 CSS3 媒体查询实现了农村信息化综合服务平台的响应式改造，解决了"传统网站只能使用单一设备访问"的困境，但其功能集中于农业资讯发布，缺乏空间交互与深度业务闭环。余洋等对"种粮宝"的案例分析则展示了数据仓与 GIS 图斑在耕地管理中的价值，但其视角是管理者而非游客。

**其三是实时通信与空间信息技术在乡村场景的应用。** WebSocket 因其全双工特性被广泛用于实时监控，但国内多数乡村系统仅将其用于即时消息，较少用于核心业务数据（如浏览日志、实时流量统计）的多端同步；GIS 应用则多集中于宏观农田溯源，针对具体村落与果园的轻量级地图标注与移动端小屏优化研究相对匮乏。

#### 1.3.2 国外研究现状

国外在农业农村信息化方面起步较早，更侧重空间信息的深度整合与数据标准建设。

在平台设计与数据协同方面，Lutpiah 等采用瀑布模型与 PHP + MySQL 为印度尼西亚 Teluk Sikumbang 村开发了基于 Web 的村级信息系统，包含村情介绍、新闻公告、图集、在线投诉与后台统计等模块，并按村民、管理员、村长三种角色完成黑盒测试。该研究解决了基础信息发布问题，但作者在结论中坦言系统缺少电子办件、交互式村庄地图与更安全的身份认证，且整体架构偏单体、缺乏多端协同与实时处理能力。Chen 与 Song 基于中国 30 个省份 2010—2022 年的面板数据，采用耦合协调模型分析了数字乡村建设与国家创新体系的协同发展，发现多数省份的耦合协调水平显著提升，且经济发达的东部地区（含浙江）长期处于高耦合区间；同时警示对数字技术的偏重可能扩大具备数字能力地区与受基础设施限制地区之间的差距。

在轻量化 WebGIS 与交互体验方面，国外研究呈现从"静态展示"向"探索型交互"转变的趋势。针对乡村场景的 WebGIS 架构研究表明，在村级或特定资源尺度上，用户更倾向于直观、有明确业务指向的空间浏览体验，而非复杂的空间分析模型。这提示移动端地图设计应聚焦于"哪里有资源、距离多远、如何前往"三个核心问题，而非叠加过多图层。

#### 1.3.3 研究现状评述

综合来看，既有研究在三个层面为本课题提供了基础，也留下了空白：

1. **宏观测度精细，微观系统粗糙**——面板数据与项目统计能够刻画区域差异，但缺少可直接落地的轻量系统；
2. **功能基线齐备，空间与实时能力缺失**——村级信息系统的最小功能集已被验证，但交互式地图与实时同步仍属少见；
3. **评价偏重"嵌入"，忽视"赋能"**——平台使用率、下载量等易量化指标被广泛采用，而"游客是否真的因此找到了目的地"缺乏衡量。

本文的切入点是：以海宁市为案例，用 WebGIS 把分散的资源"放回地图"，用 WebSocket 把隐形客流"变成可见数据"，并以零支付导流规避乡村交易链路的现实约束。

### 1.4 主要研究内容

本文围绕一个双端协同的农文旅信息平台，完成以下四项工作：

1. **基于 WebGIS 的资源空间展示**：将资源点位的经纬度与业务数据关联，Web 端与小程序端均加载海宁市地图并标注资源，支持分类筛选与信息弹窗。
2. **特色资源的发布与多端导览**：Web 后台提供资源的增删改查与上下架，小程序端提供分类浏览、详情展示与外部链接导流。
3. **平台运行数据的可视化大屏**：基于 ECharts 展示今日 PV/UV、外链点击转化率、资源类别与镇街分布、热度排行与分时趋势，数据全部来自系统真实日志。
4. **基于 WebSocket 的多端实时同步**：小程序端产生浏览行为后，后端落库、统计并广播，Web 大屏即时更新，替代 HTTP 轮询。

## 第 2 章 需求分析

### 2.1 可行性分析

**技术可行性**。Flask 是成熟的 Python 微框架，核心由 Werkzeug 与 Jinja2 构成，不强制绑定数据库与前端框架，适合中小型业务场景；SQLAlchemy 提供成熟的对象关系映射与连接池管理；Flask-JWT-Extended 提供标准化的令牌签发与校验；Flask-SocketIO 基于 python-socketio，可在 eventlet 协程模型下支撑长连接；Vue3 与 Element Plus 覆盖后台管理所需的表格、表单、弹窗等组件；ECharts 是国内数据可视化的事实标准；Leaflet 轻量且支持 GeoJSON 渲染；Uni-app 支持一套代码编译到小程序与 H5。上述技术在社区活跃度、文档完备度与部署成本方面均满足本科毕设的工程要求。

**经济可行性**。全部技术均为开源且免费；开发与部署可在普通个人计算机上完成；运行时资源占用低（MySQL 单实例 + Redis 便携版 + 单进程 Flask），无需购买云服务器即可完成演示与答辩。

**操作可行性**。平台的角色边界清晰：游客只使用小程序，无需注册与培训；运营人员只使用 Web 后台，界面与常见的后台管理系统一致；所有写操作均有表单校验与二次确认，误操作成本低。

### 2.2 用户角色与业务场景

平台设置两类使用者：**游客**与**平台运营/管理人员**。前者通过微信小程序浏览资源，后者通过 Web 后台维护内容并查看数据。

不设置"农户自主注册发布"角色，理由有二：一是乡村中小主体的数字素养与持续运营意愿有限，自主发布容易产生僵尸信息；二是运营方代维护虽牺牲了规模，却换来了数据质量与审核可控性。

### 2.5 核心业务流程

平台的五条核心流程如图 3-2 至图 3-6 所示（图号见第 3 章）：浏览触达大屏、资源发布同步、地图导览导航、零支付外链导流、异常降级。其中第一条是全平台的主链路：

```
游客进入详情页 → 上报 view 事件 → 后端写日志
```

## 第 3 章 系统设计

### 3.1 设计原则

1. **单一数据源**：MySQL 为唯一事实来源，Redis 仅作缓存与消息通道，不产生数据分歧。
2. **职责分离**：写操作只能从 Web 后台进入，小程序端只读；游客端匿名，管理端鉴权。
3. **降级优先于报错**：缓存不可用则回源，广播失败不影响写库结果。
4. **轻量化**：不引入消息中间件、不依赖第三方瓦片服务，保证在普通计算机上可完整演示。
5. **可演进**：接口与模块划分预留扩展点（如对象存储、限流、多实例广播）。

### 3.2 总体架构设计

系统采用分层架构，自下而上分为基础设施层、数据访问层、业务服务层与表现层，表现层按终端拆分为三个前端工程。各层的组成与职责见表 3-1。

**表 3-1 系统分层架构**

|层次|组成|主要职责|
|-|-|-|
|表现层|Web 管理后台（Vue3 + Element Plus）、Web 数据大屏（Vue3 + ECharts）、微信小程序（Uni-app）|界面呈现与交互；小程序端负责埋点上报；大屏订阅实时事件|
|业务服务层（Flask）|认证鉴权、资源服务、足迹服务、统计服务、实时服务|参数校验、业务编排、数据聚合、事件广播|
|数据访问层|SQLAlchemy ORM、pymysql 驱动|对象与表映射、连接池管理、事务控制|
|基础设施层|MySQL 8.0、Redis 5.0、GeoJSON 底图|持久化存储、缓存与消息通道、空间底图资源|

三层之间的调用关系是：表现层只通过 HTTP 或 WebSocket 与业务服务层交互，不直接访问数据库；业务服务层通过 SQLAlchemy 访问 MySQL，通过缓存工具访问 Redis；GeoJSON 底图作为静态资源随前端部署，不经过后端。

后端采用应用工厂模式组织：`extensions.py` 统一持有 JWTManager 与 SocketIO 实例，避免模块循环引用；`api/` 下按业务拆分为认证、资源、足迹、统计四个蓝图；`ws/events.py` 负责命名空间事件与广播；`utils/` 提供响应体封装、鉴权装饰器与缓存工具。这种划分使新增一个业务模块只需增加一个蓝图文件，而不必改动入口。

### 3.3 功能模块设计

依据第 2 章的需求，系统划分为四大模块（图 3-2）。

**（1）资源展示模块**。对外提供列表、详情、地图点位与筛选元数据四类只读接口。列表仅返回上架资源，详情接口无副作用；地图点位接口返回精简结构（不含富文本），供两端直接打点。

**（2）资源管理模块**。面向运营人员，提供增删改与上下架。写入前依次校验：必填字段、类别枚举、坐标数值合法性、名称唯一性。成功写入后触发缓存失效并记录审计日志。

**（3）数据统计模块**。以"今日"为主要时间窗口，计算 PV（浏览事件数）、UV（去重设备数）、外链点击数与转化率，并输出类别分布、镇街分布、热度排行与 24 小时分时序列。

**（4）实时同步模块**。服务端在写入足迹后向 `/ws` 命名空间广播 `new\_data` 事件，载荷同时包含日志对象、目标资源摘要与最新指标，使大屏无需回查即可更新。

### 3.4 数据库设计

数据库 `jiaxing\_rural` 采用 utf8mb4 字符集，共三张表：`admin`（管理员）、`attraction`（资源点位）、`system\_log`（系统日志）。

**（1）实体关系**。`admin` 与 `system\_log` 为一对多（可空），`attraction` 与 `system\_log` 通过 `target\_type` + `target\_id` 的多态方式关联，从而让同一张日志表既能记录后台操作，也能记录游客行为。

**（2）关键字段设计**。资源表的经纬度采用 `DECIMAL(10,6)` 与 `NUMERIC(10,6)`，精度约 0.1 米，足以表达村级点位；日志表的 `session\_id` 为 64 位字符串并建索引，用于 UV 去重；`source` 区分 `web` 与 `miniprogram`；`action` 建索引以加速按行为筛选。

### 3.6 关键技术设计

#### 3.6.1 WebGIS 方案

Web 端采用 Leaflet + 本地 GeoJSON：将海宁市行政边界（约 15 KB）作为底图直接渲染，不依赖第三方瓦片服务。这一选择带来两个好处：其一，答辩现场即使断网也能显示海宁轮廓与点位；其二，规避了国内地图坐标系（GCJ-02）与 WGS84 混用带来的偏移问题。

小程序端使用微信原生 `<map>` 组件，标记通过 `markers` 数组传入，并配置 `callout` 实现点击名牌效果。为缓解小屏标记重叠，地图页提供类别筛选条，通过降低同屏标记数量而非引入聚合算法来控制复杂度——这是针对"资源总量为十几个"这一实际情况的务实选择。

#### 3.6.2 实时同步方案

实时链路基于 Socket.IO 的 `/ws` 命名空间。服务端在足迹落库后调用 `socketio.emit("new\_data", payload, namespace="/ws")` 广播。这里有一个易错点：必须使用 `socketio.emit`（全局广播）而不是 `flask\_socketio.emit`（只回给当前请求方），因为触发方是普通 HTTP 请求，本身并不持有 WebSocket 连接。

多实例部署时，广播需要跨进程传播，因此引入 Redis 作为消息通道（`message\_queue`）。启动时若 Redis 可用则启用，否则退回进程内广播，保证开发环境无需强制依赖。

客户端侧实现指数退避重连（1 秒起，最大 8 秒），并在断线时以 15 秒周期轮询 `overview` 接口兜底，避免大屏长时间静止。

#### 3.6.3 缓存与失效方案

地图点位与筛选元数据属于典型的"读多写少"数据，缓存键分别为 `jrt:attraction:map`（TTL 60s）与 `jrt:attraction:meta`（TTL 120s）。后台任何写操作（新增、编辑、删除、上下架）成功后都会删除这两个键，保证"后台改了、地图立刻可见"。

缓存实现遵循"失败即降级"：连接超时设为 1 秒，失败后 5 秒内不再重试，所有读写异常都被捕获并返回未命中，因此 Redis 故障只会让接口变慢，而不会让接口报错。

#### 3.6.4 认证与安全方案

密码使用 Werkzeug 的 `pbkdf2:sha256` 加盐哈希存储；登录成功后签发有效期 12 小时的 JWT，`identity` 存管理员主键（新版库要求为字符串），并在附加声明中携带用户名与角色。所有受保护接口通过 `role\_required` 装饰器统一校验登录态与账号状态，未登录、令牌过期、令牌伪造三类异常分别映射为统一的 401 响应。

此外，登录失败与成功均写入 `system\_log`，写操作记录客户端 IP 与 User-Agent，为后续审计留痕。

### 4.2 后端实现

后端共 17 个源文件，按职责分为入口、配置、模型、接口、工具与实时六部分。

**（1）应用工厂与扩展初始化。** 入口文件在执行任何网络库导入前先完成 eventlet 的猴子补丁，随后创建 Flask 实例并依次初始化 CORS、SQLAlchemy、JWT 与 SocketIO：

```python
try:
    import eventlet
    eventlet.monkey\_patch()
except Exception:
    ASYNC\_MODE\_FALLBACK = "threading"

def create\_app(config\_name=None):
    app = Flask(\_\_name\_\_)
    app.config.from\_object(get\_config(config\_name))
    app.json.ensure\_ascii = False
    CORS(app, resources={r"/api/\*": {"origins": "\*"}})
    db.init\_app(app); jwt.init\_app(app)
    message\_queue = \_detect\_message\_queue(app)   # Redis 可用则用 Pub/Sub
    socketio.init\_app(app, async\_mode=..., message\_queue=message\_queue)
    register\_error\_handlers(app); register\_jwt\_handlers(app)
    register\_blueprints(app); register\_socket\_events()
    return app
```

`json.ensure\_ascii = False` 使中文在响应中直接输出，便于调试与阅读；错误处理器把 404/405 与未捕获异常统一转成 JSON。

**（2）数据模型。** 三张表以声明式模型定义，统一 `InnoDB + utf8mb4`。模型内部的 `to\_dict()` 负责把 `Decimal` 类型的经纬度转成 `float`，避免前端收到字符串后无法直接用于地图；`Admin.to\_dict()` 刻意不含 `password\_hash`，从源头杜绝敏感字段外泄。

**（3）认证实现。** 登录时先校验字段完整性，再按用户名查库并比对密码哈希。为防账号枚举，账号不存在与密码错误返回同一条提示：

```python
admin = Admin.query.filter\_by(username=username).first()
if admin is None or not admin.check\_password(password):
    SystemLog.record(action="login\_failed", ...)
    return fail("账号或密码错误", 401, 401)
token = create\_access\_token(identity=str(admin.id),
                            additional\_claims={"role": admin.role},
                            expires\_delta=expires)
```

`role\_required` 装饰器封装了"取令牌 → 查管理员 → 校验状态与角色"的固定流程，避免在每个接口重复编写。

**（4）足迹接口。** 这是全平台最关键的写接口，实现顺序为：参数校验 → 查目标资源 → 写日志 → 原子自增 → 统计 → 广播：

```python
log = SystemLog.record(action=action, target\_type=target\_type,
                       target\_id=target\_id, source=source,
                       session\_id=session\_id, ip=\_client\_ip())
if target is not None and action == "view":
    db.session.execute(
        update(Attraction).where(Attraction.id == target.id)
        .values(view\_count=Attraction.view\_count + 1))
    db.session.commit()
metrics = \_today\_metrics()
\_broadcast({"event": action, "log": log.to\_dict(),
            "target": {...}, "metrics": metrics,
            "timestamp": ...})
```

浏览量采用 `UPDATE ... SET view\_count = view\_count + 1` 而非"读—改—写"，从根本上避免并发丢更新。即使 `target\_id` 指向不存在的资源，日志仍会写入并在 `detail` 中标注 `target\_missing`，以便排查前端误传。

**（5）缓存实现。** 缓存工具以"惰性连接 + 失败重试间隔"实现。首次调用时尝试连接并 `PING`，失败则记录日志并在 5 秒内不再重试，避免每次请求都被 1 秒的连接超时拖慢：

```python
def get\_redis():
    global \_client, \_last\_attempt
    if \_client is not None:
        return \_client
    if \_last\_attempt and time.time() - \_last\_attempt < RETRY\_INTERVAL:
        return None
    \_last\_attempt = time.time()
    try:
        client = redis.Redis(..., protocol=2, socket\_connect\_timeout=1)
        client.ping(); \_client = client
    except Exception:
        \_client = None
    return \_client
```

> 实现中曾遇到的兼容问题：redis-py 8.x 默认使用 RESP3 协议，连接时会发送 `HELLO 3`，而 Redis 5 不支持该命令，导致连接失败。最终通过固定 `redis-py==5.0.8` 并显式指定 `protocol=2` 解决。

### 4.3 Web 端实现

Web 端为独立的 Vite 工程，目录按 `api / router / store / layout / components / views` 组织。

**（1）请求层。** 基于 axios 封装统一实例：请求拦截器自动附加 `Authorization` 头；响应拦截器拆解 `{code, message, data}` 信封，并对 401 做统一处理——清除本地令牌并跳转登录页，避免在每个页面重复判断。

**（2）路由与鉴权。** 使用 `createWebHistory` 的 history 模式，配合全局前置守卫：目标路由若未标记 `public` 且本地无令牌，则重定向到登录页并携带 `redirect` 参数，登录成功后原路返回。大屏被设计为独立全屏路由，不套用后台布局。

**（3）资源管理页。** 采用"筛选卡片 + 表格 + 弹窗表单"的经典后台结构。表格中的上下架使用开关组件，切换即调用 `PATCH /status`；删除使用确认弹窗；新增与编辑共用同一弹窗，通过 `editingId` 区分。

**（4）数据大屏。** 大屏是本项目最能体现技术特点的页面，由五部分组成：四张 KPI 卡、24 小时分时折线、类别饼图、镇街柱图、热度排行条形图，以及实时足迹滚动流。布局使用 CSS Grid 三列，1400 px 以下自动降为两列。

实时更新通过 socket.io-client 完成：

```javascript
socket = io('/ws', {
  path: '/socket.io',
  transports: \['websocket', 'polling'],
  reconnectionDelay: 1000,
  reconnectionDelayMax: 8000
})
socket.on('new\_data', (payload) => {
  overview.today.pv = payload.metrics.pv      // 直接采用服务端统计，避免口径不一
  overview.today.uv = payload.metrics.uv
  // 当前小时 +1、热度排行自增、足迹入流、KPI 脉冲动画
})
```

其中"指标直接采用服务端返回值"是一个重要设计：客户端不自行累加 PV，从而保证大屏数字与数据库统计永远一致。

**（5）GIS 组件。** Leaflet 组件加载 `public/gis/haining.json` 后以 `L.geoJSON` 渲染边界，并据此 `fitBounds`。标记使用 `L.divIcon` 自定义样式，按类别着色（古镇橙、果园绿、村落蓝、景区紫），点击弹出简介。组件对外只暴露 `markers` 一个属性，便于在概览页与大屏复用。

### 4.4 小程序端实现

小程序基于 Uni-app（Vue3）开发，编译目标为微信小程序，同时可编译 H5 预览。

**（1）工程结构。** `pages.json` 定义五个页面与三个 tabBar；`manifest.json` 配置小程序 AppID（开发期为测试号）、位置权限与 `requiredPrivateInfos`；`config.js` 集中管理后端地址，便于真机调试时改为局域网 IP。

**（2）请求层。** 封装 `uni.request` 为 Promise，自动拼接查询串并拆解统一响应体，失败时抛出带业务提示的 Error，由页面统一 `showToast`。

**（3）埋点实现。** 埋点是"小程序 → 大屏"链路的起点。工具函数负责组装固定字段并静默上报：

```javascript
export function track(action, targetType, targetId, detail) {
  post('/log', {
    action, target\_type: targetType, target\_id: targetId,
    source: 'miniprogram', session\_id: getSessionId(), detail
  }).catch(() => {})   // 埋点失败不得打断浏览
}
```

`session\_id` 首次进入时生成并存入本地存储，格式为 `mp-时间戳-随机串`，仅用于 UV 去重，不含任何个人身份信息。

**（4）地图页。** 使用原生 `<map>` 组件，`markers` 由点位接口计算得出，并附带 `callout` 配置实现点击显示名称。页面顶部为类别筛选条，点击标记在底部弹出资源卡片，提供"导航"与"查看详情"两个动作；"导航"调用 `uni.openLocation` 唤起微信内置地图，避免自建导航逻辑。

**（5）详情页。** 进入即上报 `view`，并把资源写入本地浏览历史。外链按钮的处理遵循零支付原则：

```javascript
function onExternal() {
  track('click\_external', 'attraction', detail.value.id, ...)
  uni.setClipboardData({ data: detail.value.external\_url, success: () => {
    uni.showModal({ title: '链接已复制', content: '小程序内无法直接打开外部商城…' })
  }})
}
```

由于微信小程序不允许直接打开第三方商城链接，采用"复制 + 提示"是最稳妥的导流方式；若后续配置业务域名，可改为 `web-view` 页面承载。

### 4.5 多端实时链路实现

完整链路的时序如图 4-1（对应 `fig\_02.png`）所示，可归纳为六个步骤：

1. 小程序请求详情，后端返回资源数据（无副作用）；
2. 小程序渲染完成后调用 `/api/log` 上报 `view`；
3. 后端写入 `system\_log`，并对 `attraction.view\_count` 做原子自增；
4. 后端在同一请求内计算今日指标（PV/UV/外链点击/转化率）；
5. 后端经 Socket.IO 向 `/ws` 广播 `new\_data`（多实例时经 Redis Pub/Sub 传播）；
6. 大屏收到事件，更新 KPI、分时序列、热度排行与实时足迹。

链路中有两处"防错"设计：广播使用全局 `socketio.emit` 而非请求上下文内的 `emit`；广播异常被捕获，写库成功即向客户端返回成功，避免因推送失败导致游客端报错。

### 5.5 缺陷记录

测试过程中发现并修复 6 个问题，其中三个属于环境与依赖兼容问题，两个属于可用性缺陷，一个属于功能缺失：

|编号|现象|根因|处理|
|-|-|-|-|
|BUG-01|前端构建报 `esbuild ... Access is denied`|构建工具清理系统临时文件被拒|将 `TEMP` 指向项目内目录|
|BUG-02|Redis 连接失败|redis-py 8.x 默认 RESP3，Redis 5 不支持 `HELLO`|固定 5.0.8 并指定 `protocol=2`|

|BUG-05|Redis 恢复后长时间仍不可用|连接失败结果被永久缓存|引入 5 秒重试间隔的惰性重连|

## 第 6 章 总结与展望

### 6.1 工作总结

本文围绕"数字赋能视域下乡村农文旅资源如何被看见"这一问题，以嘉兴海宁市为空间范围，完成了一个双端协同信息平台的设计与实现。主要工作与结论如下：

**（1）明确了产品定位。** 通过文献与案例梳理发现，本地已有的"种粮宝"等平台服务于监管侧，通用 OTA 与电商平台又存在信息不本地、入驻门槛高的问题。据此将平台定位为"面向公众的轻量级乡村农文旅入口"，并以"零支付纯导流"规避交易链路的现实约束。

**（2）完成了双端协同架构。** Web 管理端与微信小程序端共用同一套 Flask 后端与 MySQL 数据库，从架构上消除了"多端两套数据"的隐患；写入入口唯一，小程序只读，保证了数据一致性。

**（3）实现了 WebGIS 空间展示。** Web 端以本地 GeoJSON 为底图，摆脱对在线瓦片服务的依赖，断网也能演示；小程序端使用原生地图组件并配合类别筛选控制标记密度。

**（4）打通了实时数据链路。** 以"上报—落库—统计—广播—渲染"为主线，用 Socket.IO + Redis Pub/Sub 实现了秒级推送，并用指数退避与兜底轮询保证弱网下的连续性。

**（5）用真实数据验证了效果。** 34 个用例全部通过；压测表明 Redis 缓存使地图接口平均延迟降低约 70%、吞吐提升约 3.3 倍；Redis 停机时 HTTP 服务不中断，恢复后 7 秒自动重连。

### 6.2 不足与展望

**（1）空间数据的精度有待提升。** 当前点位坐标取自公开地图的近似值，与微信地图使用的 GCJ-02 坐标系存在偏移。后续应统一坐标系，并通过实地采点或调用地理编码接口进行校准。

**（2）并发能力受单进程限制。** 当前以单进程 eventlet 运行，虽然已预留 Redis 消息通道，但尚未做多实例部署验证。后续可用 Gunicorn 多 worker 配合 Nginx 反向代理，验证水平扩展下的广播一致性。

**（3）内容运营能力偏弱。** 目前只支持资源与足迹，尚无资讯、活动、图片上传等运营型内容，资源图片也只有字段而缺少上传服务。后续可接入对象存储，补齐富媒体与资讯模块。

**（4）缺少安全加固。** 未实现接口限流，恶意高频上报可以刷高 PV；也未做 CSRF 与请求签名的防护。后续可增加基于 IP 与会话的令牌桶限流，并对写接口校验来源。

**（5）评价体系仍偏"嵌入"。** 平台目前统计的是使用量指标（PV/UV/点击率），尚未衡量"赋能"效果（例如游客是否真的成行）。这与姚清晨等指出的"软硬失衡"问题一致，未来可通过问卷回访或到访核销来补充效果评估。

尽管如此，本文所实现的平台已经完整覆盖了"看见资源—找到目的地—反馈数据"的闭环，并在轻量级技术栈下验证了多端协同与实时同步的可行性，可为县域尺度的乡村农文旅信息化建设提供一份可复制的工程样本。
