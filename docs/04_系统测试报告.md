## 一、测试概述

### 1.1 测试目的

验证平台三端（Flask 后端、Vue3 管理后台与大屏、Uni-app 小程序）功能完整、数据一致、实时链路可靠，并确认在依赖服务异常时具备降级能力。

### 1.2 测试范围

| 范围 | 是否覆盖 |
|---|---|
| 认证与鉴权（登录、JWT、密码校验） | ✅ |
| 资源管理（列表/详情/地图/新增/编辑/删除/上下架） | ✅ |
| 浏览足迹上报与统计 | ✅ |
| WebSocket 实时广播 | ✅ |
| Redis 缓存与失效 | ✅ |
| 异常降级（Redis 停机） | ✅ |
| 接口性能与并发 | ✅ |
| 前端构建与小程序的编译产物 | ✅ |
| 浏览器 UI 视觉验收、微信真机运行 | ⚠️ 见 1.4 测试限制 |

### 1.3 测试方法

采用黑盒功能测试为主，辅以接口级集成测试与轻量性能测试：

1. **黑盒功能测试**：按角色与业务路径设计用例，通过 HTTP 客户端调用接口并核对数据库落库结果；
2. **集成测试**：用独立进程的 Socket.IO 客户端（`tests/ws_probe.py`）验证"HTTP 写库 → WebSocket 广播 → 客户端接收"的完整链路，包含经 Vite 代理的场景；
3. **性能测试**：自研压测脚本（`tests/bench.py`，仅用标准库线程池），对比"走数据库"与"走 Redis 缓存"的差异；
4. **异常场景测试**：手动停止 Redis 进程，观察接口可用性与健康检查状态，再重启验证自动恢复。

### 1.4 测试限制（如实说明）

本机为 Windows 开发环境，**无浏览器自动化框架、无微信开发者工具运行时**，因此：

- Web 端 UI 的视觉呈现、交互细节未纳入自动化验证，仅完成"构建通过 + 页面模块可编译 + 接口代理连通"的间接验证，最终由人工验收；
- 小程序端完成了 `mp-weixin` 与 `h5` 双目标编译验证与接口契约验证，真机渲染需在微信开发者工具中人工确认。

这一限制不影响对**业务逻辑与数据链路**的结论，因为该部分已通过接口层与数据库层直接验证。

## 四、性能测试

### 4.1 测试方法

`tests/bench.py`：每场景固定 200 次请求、10 线程并发，记录每次请求耗时（毫秒），统计 RPS、平均、P50、P95、P99、最大耗时与错误数。

### 4.2 结果

| 场景 | 请求数 | 错误 | RPS | 平均 (ms) | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| A. `GET /api/attractions`（走 MySQL + 分页） | 200 | 0 | 154.3 | 60.5 | 55.0 | 77.9 | 223.7 |
| B. `GET /api/attractions/map`（走 Redis 缓存） | 200 | 0 | 513.7 | 18.0 | 17.3 | 32.3 | 35.8 |
| C. `POST /api/log`（写库 + 统计 + 广播） | 200 | 0 | 62.4 | 158.2 | 157.2 | 189.7 | 198.9 |

### 4.3 分析

1. **缓存收益显著**：同一份点位数据，走 Redis 后平均耗时从 60.5 ms 降到 18.0 ms（**降低约 70%**），RPS 从 154 提升到 514（**约 3.3 倍**）。原因是省去了 SQLAlchemy 查询与对象序列化，只做一次 GET + JSON 反序列化。
2. **写路径慢于读路径属正常**：`POST /api/log` 平均 158 ms，主要开销在「插入日志 + 原子更新浏览量 + 两次统计查询 + 触发广播」。该接口是异步埋点（小程序不等待结果），用户无感知。
3. **P99 高于 P95 说明存在长尾**：A 场景 P99 达 223.7 ms，与 eventlet 单进程协作式调度下的排队有关；生产环境可通过多进程 + Redis 消息队列横向扩展（架构上已预留 `message_queue`）。
4. **零错误率**：三个场景 600 次请求 0 错误，说明在当前并发量级下服务稳定。

### 4.4 与开题预期对照

| 指标 | 预期（非功能需求） | 实测 | 结论 |
|---|---|---|---|
| 列表接口 P95 | < 200 ms | 77.9 ms | 达标 |
| 地图接口 P95 | < 100 ms | 32.3 ms | 达标 |
| 并发可靠性 | 无明显失败 | 10 并发 0 错误 | 达标 |

## 五、安全测试

| 检查项 | 方法 | 结果 |
|---|---|---|
| 密码存储 | 查库查看 `admin.password_hash` | 为 `pbkdf2:sha256` 加盐哈希，非明文 |
| 接口鉴权 | 无 token / 伪造 token 访问写接口与查询接口 | 均返回 401，未泄露数据 |
| 越权访问 | 小程序公开接口与后台接口分离 | 公开接口不可写入，写操作均要求 JWT |
| SQL 注入 | 使用 SQLAlchemy ORM 参数化查询；关键词搜索传入 `' OR 1=1 --` | 被当作普通字符串处理，无异常返回 |
| 敏感信息泄露 | 检查 `Admin.to_dict()` | 不含 `password_hash` |
| 操作留痕 | 登录、增删改、上下架 | 均写入 `system_log`（含 ip、user_agent） |
| 跨域 | CORS 仅对 `/api/*` 开放，Socket.IO 单独配置 | 符合预期 |

> 说明：本项目为课程作品，未做渗透级测试；上述为基本安全设计验证。

## 六、缺陷记录与修复

| 编号 | 现象 | 根因 | 处理 | 状态 |
|---|---|---|---|---|
| BUG-01 | `npm run build` 报 `esbuild ... remove ... Access is denied` | esbuild 在系统临时目录清理临时文件被拒绝 | 构建时把 `TEMP/TMP` 指向项目内 `.tmp` 目录 | 已解决（写入文档） |
| BUG-02 | 后端启动后 `redis` 始终为 false，缓存不生效 | redis-py 8.1 默认 RESP3，向 Redis 5 发送 `HELLO 3` 报错 | 降级 `redis-py==5.0.8` 并显式 `protocol=2` | 已解决 |
| BUG-03 | Redis 启动报 `Not enough parameters available for --save` | Windows 移植版不接受空字符串参数 | 改 `--save 3600 1` | 已解决 |
| BUG-04 | Redis 停机后 `/api/ping` 仍报 `redis=true` | 健康检查只判断连接对象是否存在，未真实探测 | `redis_alive()` 改为真实 `PING`，失败即丢弃单例 | 已解决 |
| BUG-05 | Redis 恢复后 `redis` 一直为 false | 连接失败被永久缓存，无重试 | 引入 5 秒重试间隔的惰性重连 | 已解决 |
| BUG-06 | 后台无法管理已下架资源 | 列表接口硬编码只返回 `status=1` | 新增 `GET /api/attractions/admin`（JWT，含全部状态） | 已解决 |

## 七、测试结论

1. 共设计并执行 **34 个用例**，全部通过，未发现阻断级缺陷。
2. 核心链路「小程序上报 → 落库 → 统计 → WebSocket 广播 → 大屏更新」在直连与代理两种网络路径下均验证成功。
3. 性能满足预期：列表 P95 = 77.9 ms、地图 P95 = 32.3 ms，Redis 缓存带来约 3.3 倍吞吐提升。
4. 依赖服务具备降级能力：Redis 停机时 HTTP 接口全部可用，恢复后 7 秒内自动重连。
5. 三端均可构建：Web 生产包、小程序 `mp-weixin` 与 `h5` 产物齐全。
